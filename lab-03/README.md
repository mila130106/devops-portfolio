# Лабораторна робота 3 — Власний DevOps-інструментарій

У теці `lab-03/` зібрано три інструменти автоматизації з довідкою `--help`, кодами виходу, перевіркою параметрів, журналюванням та документацією:

* `backup.sh` — скрипт резервного копіювання з ротацією архівів
* `api_monitor.py` і `config/endpoints.json` — монітор доступності API з класифікацією збоїв та сповіщеннями
* `hooks/pre-commit` і `hooks/pre-push` — локальні Git-хуки для перевірок перед комітом та відправкою

Зміни потрапляють у гілку `main` через Pull Request із власної гілки.

## 1. Скрипт резервного копіювання (`backup.sh`)

Скрипт створює стиснений архів `.tar.gz` вказаної теки-джерела з часовою міткою формату `YYYY-MM-DD-HHMMSS` (для правильного хронологічного сортування за іменем) та зберігає лише `N` найновіших архівів цього джерела (типово `5`). Сторонні файли у теці призначення не видаляються, а шляхи з пробілами підтримуються.

### Параметри запуску
* `--source <шлях>` — обов'язкова тека, яку архівуємо
* `--dest <шлях>` — обов'язкова тека, куди складаємо архіви (створюється автоматично, якщо відсутня)
* `--keep <N>` — скільки останніх копій цього джерела зберігати (необов'язковий, типово `5`)
* `--dry-run` — показує заплановані дії без створення та видалення файлів
* `--help` — виводить призначення, параметри, коди виходу та приклад запуску

### Пояснення `set -euo pipefail` своїми словами
* **`-e` (`errexit`)** — змушує скрипт негайно завершитися при першій команді з ненульовим кодом виходу. *Без нього* скрипт міг би проігнорувати помилку створення архіву чи видалення старих копій і піти далі, записавши невірний результат або неповний бекап.
* **`-u` (`nounset`)** — забороняє використовувати неоголошені змінні та одразу завершує роботу з помилкою при зверненні до них. *Без нього* одруківка в назві змінної (наприклад, `$KEP` замість `$KEEP`) перетворилася б на порожній рядок і зіпсувала шляхи чи логіку ротації.
* **`-o pipefail`** — робить так, щоб конвеєр (`cmd1 | cmd2`) повертав помилку, якщо впала будь-яка команда в ланцюжку, а не лише остання. *Без нього* помилка на початковому етапі конвеєра могла загубитися, і скрипт вважав би крок успішним.

### Приклади запуску та виводу
```bash
./lab-03/backup.sh --help
./lab-03/backup.sh --source "/tmp/my project" --dest "/tmp/backups" --keep 3
./lab-03/backup.sh --source "/tmp/my project" --dest "/tmp/backups" --keep 3 --dry-run
```
Приклад виводу в журнал:
`[2026-11-27 12:06:46] action=backup result=archived=1, deleted=1, archive_size=173B, file=lab03 src-2026-11-27-120646.tar.gz`

## 2. Монітор доступності API (`api_monitor.py`)
Перевіряє цілі з конфігу (`config/endpoints.json`), робить 1 повторну спробу при мережевій помилці, розрізняє 6 типів збоїв (`DNS_ERROR`, `CONNECTION_REFUSED`, `TIMEOUT`, `CERTIFICATE_ERROR`, `UNEXPECTED_STATUS`, `SLOW_RESPONSE`), пише JSONL у `log_file` і бере секрети сповіщень зі змінних середовища (`ALERT_WEBHOOK_URL`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`).


### Приклад конфігурації (`config/endpoints.json`)
```json
{
  "log_file": "lab-03/monitor_results.jsonl",
  "targets": [
    {
      "name": "health-check",
      "url": "[https://httpbin.org/status/200](https://httpbin.org/status/200)",
      "expected_status": 200,
      "timeout_seconds": 5,
      "slow_threshold_ms": 1500
    },
    {
      "name": "not-found-endpoint",
      "url": "[https://httpbin.org/status/404](https://httpbin.org/status/404)",
      "expected_status": 200,
      "timeout_seconds": 5,
      "slow_threshold_ms": 1500
    }
  ]
}nn### Запуск
```bash
python3 lab-03/api_monitor.py --help
python3 lab-03/api_monitor.py --config lab-03/config/endpoints.json
```

### Зєднання відхилено vs Тайм-аут
- **Зєднання відхилено (`CONNECTION_REFUSED`)**: вузол доступний і пакет дійшов до порту, але сервіс не слухає/відхилив підключення — перевіряємо, чи запущений сервіс, процес і правильний порт.
- **Тайм-аут (`TIMEOUT`)**: відповідь не прийшла вчасно (пакет відкинуто файрволом, проблема з маршрутом/мережею або сервіс завис під навантаженням) — перевіряємо мережу/файрвол, навантаження та тайм-аут.

## 3. Інтеграція з Git (`hooks/pre-commit` та `hooks/pre-push`)

У теці `lab-03/hooks/` знаходяться два хуки:
- `pre-commit` — запускає лінтер (`shellcheck` для `*.sh`, `ruff` або `py_compile` для `*.py`) лише на проіндексованих (`staged`) файлах і блокує коміт при знайдених проблемах.
- `pre-push` — запускає синтаксичні та модульні перевірки перед відправкою змін і блокує `git push`, якщо перевірки не проходять.

### Як встановити хуки
Тека `.git/hooks` не версіонується в Git, тому хуки вмикаються локально одним зі способів:
1. **Через `core.hooksPath` (рекомендовано):**
   `git config core.hooksPath lab-03/hooks`
2. **Копіюванням у `.git/hooks`:**
   `cp lab-03/hooks/pre-commit lab-03/hooks/pre-push .git/hooks/`
3. **Символічним посиланням:**
   `ln -sf ../../lab-03/hooks/pre-commit .git/hooks/pre-commit` та `ln -sf ../../lab-03/hooks/pre-push .git/hooks/pre-push`

### Чому хуки не є засобом контролю і що роблять обов'язкові перевірки в конвеєрі (CI)
Локальні Git-хуки виконуються на машині розробника і не є надійним засобом контролю, оскільки їх можна легко обійти (наприклад, прапорцем `--no-verify`), змінити локально, не встановити після клонування репозиторію або запустити в іншому оточенні, де немає потрібних лінтерів чи залежностей. Обов'язкові перевірки в конвеєрі (CI на сервері/гілці через PR/branch protection) виконуються централізовано в чистому і відтворюваному середовищі, не залежать від локальної машини розробника та можуть блокувати злиття коду в захищену гілку незалежно від локальних дій.
